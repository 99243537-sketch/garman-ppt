# 更新 v5：流式接收，解决后端 180 秒超时（2026-10-20）

谢谢 Eddy 的排查：失败全是 `upstream_error:timeout`，是 ppt-planner 等 MiniMax 整段回复等到 180 秒放弃了。

## 步骤（3 个文件都换，这次 app.js、index.html 也变了）

```
cp ppt/app.js ppt/index.html /www/www.zhaodun.work/ppt/
sudo cp ppt-planner/app.py /opt/ppt-planner/
sudo systemctl restart ppt-planner
```

.env 不用改。`REQUEST_TIMEOUT` 的含义变了：现在是「两段数据之间最长等多久」，不再是整个请求的总时长，180 就够用。

## 改了什么

- 调用 MiniMax 改为流式（stream=true）：模型边生成边传回，只要还在输出就一直等，长文档跑 5 分钟也不会被切。总时长上限是 REQUEST_TIMEOUT 的 3 倍。
- 修正请求不再用多轮对话。MiniMax 文档要求多轮时必须原样带回上一轮的 `<think>` 思考内容，我们之前没带；现在把上一版方案放进同一条提问里。
- 失败原因记得更细：`http429:…`（限流，附 MiniMax 原话）、`stream_cut@秒数`（中途断线）、`timeout@秒数` 等。
- 修正时页面提示改为「大模型正在修正」。

## 装完请验证

用一份真实文档（最好 2 万字那份）走一遍，然后：
```
sqlite3 /opt/ppt-planner/usage.db "select datetime(ts,'unixepoch','localtime'), kind, ok, chars, secs, note from usage order by ts desc limit 6"
```
如果出现大量 `stream_cut` 或报错异常，在 .env 加一行 `STREAM=0` 重启即回到原来的方式，再告诉赵老师。
